**Title**: Allow injecting a custom `OkHttpClient` (or its builder) into `Config`

**Package/version**: `com.meilisearch.sdk:meilisearch-java:0.21.0`

## Problem

`Config` constructs its HTTP transport internally and there is no way to influence it.
All four public constructors funnel into one path that ends in `new HttpClient(this)`,
and `CustomOkHttpClient` builds a default `OkHttpClient` with no configuration surface.
The full public API of `Config` (0.21.0) is:

```java
public Config(String hostUrl)
public Config(String hostUrl, String apiKey)
public Config(String hostUrl, String apiKey, JsonHandler jsonHandler)
public Config(String hostUrl, String apiKey, String[] clientAgents)
public Config(String hostUrl, String apiKey, JsonHandler jsonHandler, String[] clientAgents)
// setters generated by Lombok reach jsonHandler only; hostUrl / apiKey / httpClient / headers are final
```

This means callers cannot set **connect timeout, read timeout, call timeout, connection
pool sizing, proxy settings, TLS pinning, or interceptors**. For plain application use the
defaults are acceptable; for libraries that wrap the SDK this is a hard blocker that has
to be documented as a limitation rather than configured.

## Context / use case

We maintain a Spring Boot starter for MeiliSearch (`io.github.lamspace:meili-orm`,
<https://github.com/LamSpace/meili-orm>) that wraps this SDK. Our configuration properties
deliberately omit `connect-timeout`/`socket-timeout` and our limitations document states
the SDK provides no injection point — verified against the 0.21.0 constructor surface and
recorded in our spike notes. Users behind constrained networks or needing per-call timeouts
(e.g. long `waitForTask` polling on slow links) cannot tune transport behaviour at all
without forking the client.

## Proposed solution

Any one of these would unblock callers, roughly in order of preference:

1. Accept an existing client: `Config(String hostUrl, String apiKey, String[] clientAgents, OkHttpClient httpClient)`
   (or a builder overload), used instead of the internally constructed one when non-null.
2. Expose a narrow transport-config callback (timeouts + pool) on `Config`, keeping OkHttp
   an implementation detail — this also leaves the door open for a non-OkHttp transport later.
3. Make `HttpClient` construction a strategy interface with a default implementation.

A backward-compatible overload on `Config` plus a null check in the client factory looks like
the minimal change. Happy to contribute a PR if one of these shapes is acceptable.

## Alternatives considered

- **Reflection on the `httpClient` field** — brittle across versions and blocked under
  strong encapsulation; not viable for library consumers.
- **Wrapping/replacing the client per call** — the SDK exposes no seam below `Client` that
  would allow this.
